## Collection Specification

### Data Source

- **Provider:** Binance Spot API
- **Symbol:** BTCUSDT (Bitcoin / USDT)
- **Interval:** 1 day (candle close 23:59:59 UTC)
- **Period:** 2017-01-01 to 2026-10-05
- **Fields:** open, high, low, close, volume (OHLCV)

### Expected Dataset

```
Period:     2017-01-01 → 2026-10-05 (3,545 days)
Frequency:  Daily (excluding weekends/holidays when exchange closed)
Expected rows: ~3,500–3,550 (including any market closures)
Granularity: Exact UTC timestamps
```

### API Endpoint (Reference)

```bash
curl -s "https://api.binance.com/api/v3/klines" \
  --data-urlencode "symbol=BTCUSDT" \
  --data-urlencode "interval=1d" \
  --data-urlencode "startTime=1483228800000" \
  --data-urlencode "endTime=1728086400000" \
  --data-urlencode "limit=1000"
```

### Collection Strategy

**Batch requests by month** (Binance API limit ~1000 candles per request):

```python
for year in [2017, 2018, ..., 2026]:
    for month in [1, 2, ..., 12]:
        fetch(start=f"{year}-{month:02d}-01", end=f"{year}-{month:02d}-31")
        validate(row_count, prices, timestamps)
        append_to_dataset()
```

## Validation Requirements

### R1: Row Count Verification

```
Expected: 3,500–3,550 rows
Tolerance: ±2% (market closures acceptable)
Success Criteria: actual_rows / expected_rows ≥ 0.98
```

### R2: Gap Detection

```
For each pair of consecutive rows:
  gap = (row[i+1].timestamp - row[i].timestamp) / (86400 seconds)
  if gap > 1.1:  # >110% of 1 day
    → FLAG as unexpected gap
    → Investigate (market closure vs data missing)

Success Criteria: 0 unexplained gaps
```

### R3: Price Continuity

```
For each 30-day window:
  high[i] ≤ close[i]
  low[i] ≤ close[i]
  low[i] ≤ high[i]
  
Success Criteria: 100% compliance
```

### R4: Volume Validation

```
For each candle:
  volume > 0  (except market closed rare cases)
  volume in BTCUSDT (not BTC)
  
Success Criteria: 99%+ volume > 0
```

### R5: Timestamp Ordering

```
For all rows:
  timestamp[i] < timestamp[i+1]
  timestamp in UTC (explicit verification)
  
Success Criteria: 100% ordered
```

### R6: No Retroactive Revisions

```
Method: Collect on Day 1, then re-collect same period on Day 3+
Compare row-by-row:
  old_price vs new_price (should be identical)
  old_volume vs new_volume (should be identical)
  
Success Criteria: 0 price/volume revisions
```

## Known Risks & Mitigations

### Risk 1: Binance API Network Restricted (HTTP 451)

**Status:** Observed in current environment (2026-10-01)  
**Mitigation:** Execute collection in approved environment with Binance API access  
**Alternative:** None (CoinGecko is complementary research only)  

### Risk 2: Binance OHLCV Revision During Collection

**Probability:** Low (historical data is typically immutable)  
**Mitigation:** R6 retroactive revision check (re-collect and compare)  
**Acceptance:** 0 revisions required  

### Risk 3: Data Gaps During Exchange Downtime

**Probability:** Very low  
**Mitigation:** R2 gap detection (tolerance ±2% for market closures)  
**Acceptance:** <1% unexplained gaps  

### Risk 4: Timestamp Ambiguity (UTC vs Local)

**Probability:** Low (Binance API returns UTC explicitly)  
**Mitigation:** Verify all timestamps are UTC in manifest  
**Acceptance:** 100% verified UTC
